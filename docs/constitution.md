# 땀 관리 날씨 앱 — 프로젝트 헌법

**버전** 1.0.0 · 2026-08-19

이 문서는 **협상 불가능한 원칙**만 담는다. 모든 스펙·계획·구현·리뷰는 여기에 종속된다.
원칙을 어겨야 할 이유가 생기면, 코드를 고치는 게 아니라 **먼저 이 문서를 개정**한다.

---

## I. 도메인 순수성

`SweatDomain` 패키지는 `Foundation` 외에 아무것도 import하지 않는다.
등급 산출·보정·노출 추정은 시뮬레이터·네트워크·권한 없이 단위 테스트로 검증 가능해야 한다.

**위반 예시** — 도메인 코드에서 `import CoreLocation`, `import SwiftUI`
**검증** — 패키지 매니페스트의 의존성이 비어 있는지 CI에서 확인

---

## II. 로직과 문구의 분리

```
apparentTemperature → SweatComfortLevel → Copy / Recommendation
```

세 단계는 각각 독립적으로 교체 가능해야 한다.
구간 경계값(§V)이 아직 확정되지 않았으므로, **경계가 바뀌어도 문구·추천 코드는 손대지 않아도 되는 구조**여야 한다.

**위반 예시** — 뷰에서 `if temp > 33 { Text("땀이 많이 날 수 있어요") }`
**검증** — 문자열 리터럴이 뷰 코드에 등장하지 않는다. 모든 카피는 `Copy` 계층에서 온다.

---

## III. UX Writing 제약

이 앱은 **땀의 양을 예측하지 않는다.** 땀을 느끼거나 땀으로 불편할 *가능성*을 전달한다.

**허용** — `~일 수 있어요`, `~해보세요`, `~를 고려해요`
**금지** — 분비량 수치(`땀 500mL`), 배수 표현(`2배`), 단정(`체감온도 35℃ = 땀 매우 많음`)

안전 관련 문구(폭염, 이상 증상)는 완곡어법을 쓰지 않는다. 5·6단계의 안전 안내는 단정형을 허용한다.

**검증** — 카피 리소스 전체를 훑는 린트 테스트. 금지 패턴 정규식으로 실패시킨다.

---

## IV. 습도·풍속은 단계를 바꾸지 않는다

습도와 풍속은 **설명과 추천의 강도만** 보정한다. `SweatComfortLevel` 값에는 영향을 주지 않는다.

근거 — 기상청 체감온도 산식에 습도가 이미 반영되어 있다. 단계에 다시 더하면 이중 계산이다.

**예외** — 개인 보정(§VI)은 사용자 자가 기록에서 학습된 값이며, 이 원칙과 별개다.

**검증** — 동일 체감온도에서 습도·풍속만 바꾼 케이스가 항상 같은 단계를 반환하는 테스트

---

## V. 구간 경계는 잠정값이다

`28 / 33 / 35 / 36 / 43℃` 는 **설계 후보**다. 확정된 과학적 기준이 아니다.

- 경계값은 코드 한 곳(`SweatStage`)에만 존재한다. 하드코딩 산재 금지.
- 경계 변경이 1개 파일 수정으로 끝나지 않으면 §II 위반이다.
- UI·문서 어디에서도 이 숫자를 "확정된 의학적 기준"으로 서술하지 않는다.

---

## VI. 예측은 사용자 기록에 의해 교정된다

자가 기록은 장식이 아니라 시스템의 입력이다.

- 최소 표본 5건 미만이면 보정하지 않는다.
- 보정 폭은 ±1.5단계로 클램프한다.
- 보정이 적용되면 사용자에게 **무엇이 왜 바뀌었는지** 보여준다 (화면 12).

---

## VII. 추정치는 추정치로 표기한다

그늘·실내 비율, 실외 노출 시간은 건물 데이터 기반 **근사치**다. 가로수·캐노피·육교 하부는 반영되지 않는다.

- 분 단위 절대값보다 **두 경로의 상대 비교**를 강조한다.
- 근사 표기(`약 12분`)와 고지 문구를 UI에 노출한다.
- 데이터가 없는 지역에서는 비율 섹션을 **숨긴다.** 0%로 표시하지 않는다.

---

## VIII. 디자인 토큰 강제

Figma `Sweat App` 변수 컬렉션과 텍스트 스타일이 단일 출처다.

- 뷰 코드에 색상 리터럴·폰트 크기 리터럴을 쓰지 않는다.
- 모든 색상은 `DesignSystem` 패키지의 토큰을 경유한다.
- Figma 변수명과 Swift 심볼의 매핑 표를 `DesignSystem/README.md`에 유지한다.

**검증** — `Color(red:`, `.font(.system(size:` 패턴을 Features 타깃에서 금지하는 린트

---

## IX. 접근성은 마감 작업이 아니다

각 화면 스펙의 완료 조건에 접근성이 포함된다. 나중에 몰아서 하지 않는다.

- **색상만으로 정보를 전달하지 않는다** — 실내/실외 구간 바에 라벨 또는 패턴 병기
- 마스코트는 장식이 아니다 — `accessibilityLabel("3단계, 땀 불편 높음")` 필수
- Dynamic Type 접근성 크기에서 예보 그리드는 세로 리스트로 전환
- 텍스트 대비 4.5:1 (12px 캡션 포함)

---

## X. Swift 6 · 엄격한 동시성

- `SWIFT_VERSION = 6.0`, strict concurrency `complete`
- 경고를 남기고 넘어가지 않는다. `@unchecked Sendable`은 주석으로 이유를 남긴 경우에만.
- Repository는 `actor`. 네트워크 캐시와 재시도는 그 안에 갇힌다.

---

## XI. 스펙 없이 코드 없다

기능 구현은 항상 `specs/NNN-<slug>/spec.md` → `plan.md` → `tasks.md` 순서를 거친다.

- 스펙은 **무엇을·왜**만 적는다. 프레임워크 이름이 스펙에 등장하면 잘못 쓴 것이다.
- 계획은 **어떻게**를 적고, 헌법 위반 여부를 스스로 점검한다.
- 태스크는 커밋 단위로 쪼갠다.

버그 수정과 오탈자는 예외다.

---

## 개정

원칙 추가·삭제는 MAJOR, 내용 강화는 MINOR, 표현 수정은 PATCH.
개정 시 영향받는 스펙을 함께 갱신한다.

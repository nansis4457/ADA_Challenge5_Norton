# [000] 파운데이션 — 스펙

**상태** Approved
**브랜치** `000-foundation`
**작성** 2026-08-19

## 1. 문제

프로젝트가 Xcode 템플릿 상태다. `ContentView`는 "Hello, world!"이고,
Swift 언어 모드는 5.0, 패키지 구조도 디자인 토큰도 도메인 로직도 없다.

이 상태에서 화면부터 만들면 두 가지가 확정적으로 깨진다.

- 색상·폰트를 리터럴로 쓰게 되어 헌법 VIII이 구조적으로 위반된다
- 등급 산출 로직이 뷰에 섞여 헌법 II(로직/문구 분리)를 되돌릴 수 없게 된다

## 2. 이 기능이 끝나면

001~005의 어떤 화면이든, **토큰과 도메인 타입만 조합하면** 만들 수 있다.
등급 산출은 시뮬레이터 없이 테스트로 검증되고, 구간 경계를 바꿔도 파일 하나만 고치면 된다.

사용자에게 보이는 변화는 없다. 이건 내부 기반 작업이다.

## 3. 사용자 시나리오

해당 없음 — 사용자 대면 기능이 아니다.
대신 **개발자 시나리오**로 검증한다.

```
Given  DesignSystem 패키지가 링크된 새 View
When   개발자가 SweatButton(style: .primary, title: "다음") 을 쓴다
Then   Figma의 Button/Primary와 픽셀 단위로 일치한다
```

```
Given  체감온도 34.2℃, 민감도 보통
When   SweatStageEngine.stage(...) 호출
Then   .three 를 반환한다
```

| R9 | 등급별 문구·추천이 도메인에서 나오고, 뷰에 문자열 리터럴이 없다 | 카피 린트 |

## 6. 문구

이 스펙에서 도메인에 정의하는 카피는 6단계 메인 멘트와 추천 행동이다.
원본은 `땀_날씨앱_구간화_UI_멘트_개발가이드.md` §2, §5.

| 단계 | 메인 멘트 |
|---|---|
| 1 | 오늘은 땀 걱정이 적어요 |
| 2 | 슬슬 땀이 날 수 있어요 |
| 3 | 오늘은 땀이 많이 날 수 있어요 |
| 4 | 오늘은 더위와 땀에 주의하세요 |
| 5 | 오늘은 더위가 매우 강해요 |
| 6 | 오늘은 야외 활동을 줄여주세요 |

추천 행동은 수분·복장·경로·휴식·안전 5개 카테고리에서 단계별로 2~3개.

## 8. 미해결 질문

- [ ] **체감온도 산식 계수 검증** — `architecture.md` §5.4
      *이 브랜치를 막지 않는다.* 산식 구현은 002 담당이고, 이 스펙의 엔진은 체감온도를
      **입력으로 받는다** (plan.md §7). 다만 R3 테스트의 `34.2℃ → 3단계`는 검증 전까지 가정이다.
- [ ] **보정값의 단위가 헌법과 어긋난다** *(T031에서 발견)*
      헌법 VI는 보정 폭을 `±1.5`**단계**로 규정하는데, `SweatStageEngine`의
      `calibration` 파라미터는 **℃**다. 단계 폭이 구간마다 달라(28~33℃는 5℃,
      35~36℃는 1℃) 1:1 환산이 안 된다. 현재 `calibrationLimit = 3.0℃`는
      **근거 없는 잠정치**다. 셋 중 하나를 골라야 한다.
      1. 보정을 ℃로 유지 → 헌법 VI를 ℃ 기준으로 개정
      2. 보정을 단계 단위로 → 엔진이 단계 인덱스를 직접 이동
      3. `CalibrationEngine`(005)이 단계 오차를 ℃로 환산 → 환산 규칙을 정의
      **005 착수 전까지 결정한다.** 이 브랜치는 막지 않는다.

- [ ] **줄높이 근사가 단일 행 텍스트에는 전혀 적용되지 않는다** *(T055 대조에서 발견)*
      `lineSpacing`은 한 `Text` 안의 **줄 사이**에만 들어간다. 한 줄짜리 텍스트에는
      아무 효과가 없다. Figma는 한 줄이어도 line-height만큼 상자가 커지므로 차이가 난다.

      | | Selectable Card 높이 |
      |---|---|
      | Figma | `16×2 + 22.1 + 3 + 20.8` = **77.9pt** |
      | SwiftUI | `16×2 + 20.2 + 3 + 15.5` ≈ **70.7pt** |
      | 차이 | **약 7pt / 카드 하나당** |

      세로로 쌓이는 화면에서 누적된다. 선택지 3개면 20pt 이상 어긋난다.
      세 갈래 중 하나를 골라야 한다.
      1. **그대로 둔다** — SwiftUI 기본 조판을 따르고 Figma 높이는 참고값으로
      2. **`.frame(height:)`로 고정** — 정확하지만 Dynamic Type에서 잘림
      3. **상하 패딩으로 line-height 상자를 흉내** — `(size×ratio − 기본줄높이)/2`
         절충안이지만 폰트 기본 줄높이를 정확히 알아야 한다

      **001 착수 전 결정한다.** 화면 레이아웃이 여기에 전부 의존한다.

- [ ] **Figma 컴포넌트가 space 토큰 밖의 값을 쓴다** *(T050·T051에서 발견)*
      컴포넌트 5종을 옮기며 나온 토큰 밖 값 (`space/*` = 4·8·12·16·22·26·32):

      | 컴포넌트 | 값 | 가장 가까운 토큰 |
      |---|---|---|
      | Button 좌우 | 20 | 16 / 22 |
      | Chip 상하 | 9 | 8 |
      | Score Button 상하 | 18 | 16 / 22 |
      | Text Field 상하·좌우 | 14 / 15 | 12 / 16 |

      추가로 **Score Button의 숫자가 텍스트 스타일에 연결되어 있지 않다**
      (Semibold 20 직접 지정. `Stat/20 Bold`는 굵기가 다름).

      지금은 컴포넌트 안에 상수로 두고 주석을 달았다.
      Figma를 토큰 값으로 맞추거나, 토큰을 추가하거나, 예외로 인정하거나 셋 중 하나다.
- [ ] **Chip의 터치 영역이 44pt 미만이다** *(T051에서 발견)*
      상하 여백 9 + 텍스트 ≈ **37pt**로, Apple HIG 최소 터치 타깃 44×44pt에 못 미친다.
      시각 크기를 키우면 디자인이 바뀌고, 보이지 않는 히트 영역만 넓히면 행 높이가
      7pt 늘어난다. **디자인 결정이 필요하다** — 헌법 IX 범위.

- [x] ~~패키지를 6개로 처음부터 나눌지~~ → **2개(`SweatDomain`, `DesignSystem`)로 시작.** 나머지는 실제로 쓰이는 스펙에서 추가한다 (plan.md §1)
- [x] ~~컴포넌트 스냅샷 테스트 도구 도입~~ → **보류.** 이번엔 카탈로그 화면 육안 대조로 갈음한다 (plan.md §8)
